Data Flow — The Filter Pipeline

Four global filters (Time Period, Warehouse, Category, Order Status) drive every screen. Here is one round-trip.

1
User changes a filter
FilterBar.vue — a v-model updates a ref in the shared useFilters() singleton.
Views react
Each view watches the filter refs and calls loadData().
Build the request
getCurrentFilters() maps selectedLocation → warehouse; 'all' values are dropped.
api.js issues the call
axios serializes params → GET /api/orders?warehouse=Tokyo&category=sensors&month=Q1-2025
FastAPI filters in-memory
filter_by_month() (expands quarters) then apply_filters() (warehouse → category → status, sequential).
Validated JSON returns
Pydantic models shape the response; the view stores it in a raw ref.
Computed → render
Derived computed properties (counts, totals, top products) recalculate and the template re-renders.

05

Key Architectural Patterns

Conventions that recur across the codebase.

Singleton filter state

A single shared useFilters() instance holds the four filter refs, so a change in FilterBar instantly propagates to every subscribed view — no global store (Pinia/Vuex).

Raw refs, derived computed

Views keep server data in plain refs (allOrders, inventoryItems) and compute counts, totals, and rankings as computed properties — the frontend re-filters in JS too.

In-memory data

mock_data.py reads the JSON files once at startup into module-level lists. There is no persistence — writes are not durable and reset on restart.

Sequential server filtering

Filters are applied as ordered Python passes (warehouse → category → status), each skipped when the value is 'all'. Time period expands quarters via a quarter map.

Locale-driven currency

useI18n() supports en/ja and derives currency (USD/JPY) from the active locale; the choice is persisted to localStorage.

Parallel page loads

The Dashboard fans out with Promise.all() across summary, orders, inventory, and backlog to cut perceived latency on every filter change.
